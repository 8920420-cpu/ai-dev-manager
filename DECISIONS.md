# DECISIONS.md — журнал архитектурных решений оркестратора (ai-dev-manager)

> Зачем приняли решение, какие альтернативы рассматривались и были ОТВЕРГНУТЫ.
> Цель — не переигрывать одни и те же вопросы и не возвращаться к уже отброшенным
> подходам. Отвергнутые альтернативы попадают в реестр решений (ClickHouse
> `orchestrator.decisions`, status=rejected) и служат анти-регрессии.

## ADR-01. Синхронизация невлитой ветки перед доставкой (Git Integrator)

- **Решение:** перед доставкой ребейзить невлитую дельту стухшей сервисной ветки на
  свежий main (programmer-runner `_syncWithMain`, commit `44dfb32`; клапан
  `PROGRAMMER_SYNC_REBASE`). Git Integrator ключуется по имени ветки, а ресинк
  BLOCKED↔main разруливает `already_integrated_content`.
- **Почему:** корневой фикс лавины `cherry_pick_failed` / `stale_branch_reverts_main`
  23–24.07 — ветка отставала от main, и её доставка откатила бы main (нетто-дифф
  удалял файлы вне changed-set задачи).
- **Альтернативы:** безусловный reset Git Integrator на `deliveredCommit` SHA стухшей
  ветки — ОТВЕРГНУТ: зацикливал `stale_branch_reverts_main` и откатывал новые файлы
  main вне changed-set задачи.
- **Нельзя менять:** возвращать пропуск синка или безусловный reset на стухший SHA без
  ребейза на актуальный main.

## ADR-02. Переиспользование сервисной ветки в worktree (clean-path программиста)

- **Решение:** clean-path программиста переиспользует существующую сервисную ветку
  (`git worktree add` без `-b`), commit `2b03f0e`.
- **Почему:** пересоздание ветки вызывало шторм `worktree_ensure_failed` →
  `programmer_release_loop` при перезапуске задачи со стухшей веткой.
- **Альтернативы:** удалять и пересоздавать ветку (`branch -D` + `git worktree add -b`)
  на каждом заходе — ОТВЕРГНУТ: гонка и шторм `worktree_ensure_failed`, бесполезные
  release-циклы, стадия CODING блокируется для остальных задач.
- **Нельзя менять:** пересоздавать существующую сервисную ветку в clean-path вместо
  переиспользования.

## ADR-03. Масштабирование чтения БД — размещение пода, а не app-level split

- **Решение:** НЕ вводить разделение чтения/записи на уровне приложения; узкое место —
  сетевое размещение пода (WireGuard между площадками), а не роутинг запросов.
- **Почему:** reader-инфраструктуру завели в 11 сервисах — реально переведённых
  операций ноль; `EXPLAIN` вводит в заблуждение (не учитывает передачу результата по
  сети). Связано с памятью: `read-write-split-app-reader`.
- **Альтернативы:** направлять читающие запросы на reader-эндпоинт (app reader /
  read-write split) во всех сервисах — ОТВЕРГНУТ: 0 операций реально переведено,
  эффект даёт только размещение пода ближе к БД.
- **Нельзя менять:** заново раскатывать app-level read/write split как решение
  латентности без учёта сетевого размещения пода.
